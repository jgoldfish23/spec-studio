# Spec Studio — Plan 2 of 3: App Shell and Deal Screens — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A working browser app — Deals list plus the five-step deal flow (Lot → House → Estimate → Market → Pro forma) running on the Plan 1 engine — that saves deals in the browser ("demo mode"). The Supabase schema, row-level security and repository code are also built and tested; going live on Supabase happens in Plan 3.

**Architecture:**
- **Screens** (`src/features/`) read and write a single `DealInputs` document through a deal-editor hook. The hook recomputes `evaluateDeal` on every change and autosaves through a `Repository` interface (`src/data/`).
- **Demo mode** uses a `localStorage` repository seeded with a starter Northern Utah cost book. Supabase tables and policies are tested against a real local Postgres. The Supabase repository is checked at the HTTP boundary.
- **Engine fixes first:** Plan 1's top follow-ups are fixed before any screen is built, so the screens rest on an engine that cannot crash on bad context data.

**Tech Stack:**
- Existing: TypeScript (strict), Node ≥ 22, Zod 4, Vitest 5, fast-check.
- New: React 19, Vite, Tailwind CSS v4 (`@tailwindcss/vite`), React Router v7 (`createHashRouter`), TanStack Query v5, Testing Library + jsdom, Playwright (`@playwright/test`), `pg` (node-postgres) for database tests, `@supabase/supabase-js`.

**Spec:** `docs/superpowers/specs/2026-10-30-spec-studio-deal-analyzer-design.md` (§4, §6, §7, §8, §9). Engine follow-ups come from `docs/superpowers/plans/2026-10-30-plan-1-followups.md`. Visual reference: `docs/mockups/*.dc.html` (static HTML with inline styles — read them for layout, copy and color; they are not code to reuse).

## Review Focus

1. **Corrupt or hand-edited data in the browser store** (bad JSON, a deal failing `DealInputsSchema`, an unknown `schemaVersion`). Expected:
   - The Deals list still loads the good deals and lists each bad one with a "Remove" action.
   - Opening a bad deal shows a recoverable error, never a blank screen.
   - Tests in Tasks 6 and 11.
2. **Rapid edits while a save is in flight.** Expected: the last edit is what ends up stored, saves never land out of order, and the status ends at "Saved". Tests in Task 9.
3. **Half-typed or odd numeric input** (empty, `"$"`, `"-"`, `"1e3"`, `"1,350,000"`, pasted spaces). Expected:
   - The field keeps the text and shows an inline error.
   - The deal keeps its last valid value.
   - `onChange` never receives `NaN`.
   - Tests in Task 10.
4. **A deal whose evaluation is incomplete or invalid** (no comps, a missing price, a validation error). Expected:
   - Every step screen renders.
   - The summary strip shows "—".
   - The verdict reads "Needs info", with the missing items linked to their step.
   - Tests in Tasks 11 and 14–16.
5. **A deal URL that doesn't exist** (deleted deal, mistyped id). Expected: a "Deal not found" page with a link back to Deals. Test in Task 11.

| `conditionFactors` | each > 0 |

| `defaultTaxRate` | 0–0.1 |

| `today` | as for dates |
